GPForum — Software Engineering, Architecture Governance & Development Constitution

Prompt 45 alignment: GPForum architecture MUST be preserved through verifiable
invariants, explicit contracts, release gates, migration discipline, and
architecture checks. Intent alone is insufficient. Every new bounded context,
store, worker, plugin hook, projection, or authoritative workflow MUST document
its invariants and testing expectations.

Prompt 48 alignment: the core MUST remain small and stable. Features that are
not universally necessary belong in plugins, capabilities, or optional
subsystems. Controllers MUST validate, authorize, dispatch, and render only.
Plugin capability boundaries, cache disposability, PostgreSQL authority, and
moderation-as-core are mandatory architectural discipline.

This document defines the mandatory software engineering philosophy, architectural governance model, engineering discipline, repository organization, code ownership principles, refactoring rules, review standards, documentation expectations, and long-term maintainability strategy of GPForum.

This specification is foundational and mandatory.

⸻

Engineering Philosophy

GPForum is:

* a long-term distributed systems project;
* a security-first platform;
* an operationally sustainable architecture;
* a Perl-native engineering ecosystem.

Engineering decisions MUST prioritize:

* maintainability;
* operational predictability;
* architectural coherence;
* explicitness;
* auditability;
* long-term sustainability.

The project MUST avoid:

* accidental complexity;
* architecture drift;
* uncontrolled abstraction;
* framework-driven chaos;
* novelty-driven engineering.

⸻

Architecture Governance Philosophy

Architecture is authoritative.

The platform MUST remain:

* constitution-driven;
* invariant-aware;
* operationally disciplined.

All engineering decisions MUST comply with:

* constitutions;
* ADRs;
* architectural constraints;
* operational principles.

No implementation convenience may override:

* security;
* observability;
* scalability;
* maintainability.

⸻

Repository Philosophy

The repository is:

* a long-lived engineering artifact;
* an operational system;
* an architectural contract.

The repository MUST remain:

* structured;
* predictable;
* navigable;
* auditable.

The repository MUST avoid:

* dumping grounds;
* uncontrolled helpers;
* architectural ambiguity.

Layering Philosophy

The platform MUST maintain:

* explicit architectural layers.

Recommended layering:

* Domain
* Application
* Infrastructure
* Transport/Delivery
* Rendering

Dependencies MUST flow inward.

Business logic MUST remain infrastructure-independent.

⸻

Domain Isolation

The domain layer MUST:

* remain persistence-independent;
* remain transport-independent;
* remain rendering-independent.

The domain layer MUST NOT depend on:

* Mojolicious;
* DBIx::Class internals;
* HTTP details;
* websocket transport logic.

⸻

Infrastructure Isolation

Infrastructure concerns MUST remain isolated.

Examples:

* database access
* optional Redis/KeyDB access
* PostgreSQL-native search integration
* optional external search integration
* filesystem integration
* object storage integration

Infrastructure MUST remain:

* replaceable;
* bounded;
* operationally explicit.

⸻

Application Service Philosophy

Application services SHOULD:

* orchestrate workflows;
* enforce use-case boundaries;
* coordinate infrastructure interaction.

Application services MUST NOT:

* become giant god services;
* absorb unrelated workflows.

Application root classes MUST NOT compensate by becoming god class
applications.

The root application class MUST wire application services, not replace them.

⸻

Thin Controller Rule

Controllers MUST remain:

* thin;
* orchestration-oriented;
* validation-aware;
* authorization-aware.

Controllers MUST NOT:

* contain business logic;
* contain persistence orchestration;
* implement hidden workflow complexity.

⸻

Naming Philosophy

Names MUST remain:

* explicit;
* descriptive;
* semantically meaningful.

Forbidden naming:

* Utils
* Helpers
* Common
* Misc
* Temp

Preferred naming:

* CreateThread
* PermissionEvaluator
* SearchIndexer
* NotificationDispatcher

⸻

Module Size Philosophy

Modules MUST remain:

* bounded;
* understandable;
* responsibility-focused.

The architecture MUST avoid:

* giant god modules;
* hidden coupling;
* uncontrolled inheritance hierarchies.

⸻

Complexity Philosophy

Complexity MUST remain:

* measurable;
* minimized;
* decomposed.

The platform MUST prioritize:

* small composable units;
* explicit workflows;
* predictable execution paths.

Complexity accumulation MUST be treated as technical debt.

⸻

Refactoring Philosophy

Refactoring is mandatory.

Refactoring MUST prioritize:

* simplification;
* decomposition;
* invariant preservation;
* operational clarity.

Refactoring MUST NOT:

* silently alter behavior;
* bypass tests;
* bypass architectural rules.

⸻

Technical Debt Philosophy

Technical debt MUST remain:

* visible;
* documented;
* reviewable;
* intentionally accepted.

Hidden architectural debt is prohibited.

⸻

Architectural Drift Prevention

The platform MUST actively resist:

* uncontrolled coupling;
* framework leakage;
* abstraction sprawl;
* dependency explosion;
* hidden infrastructure assumptions.

Architectural consistency is mandatory.

⸻

ADR Philosophy

Architectural Decision Records SHOULD exist for:

* major architecture changes;
* persistence changes;
* infrastructure changes;
* protocol changes;
* distributed systems behavior.

ADRs MUST include:

* context;
* decision;
* consequences;
* alternatives considered.

⸻

Documentation Philosophy

Critical systems MUST remain documented.

Documentation SHOULD include:

* architectural intent;
* invariants;
* failure assumptions;
* operational expectations;
* scaling assumptions.

The platform MUST remain understandable by future maintainers.

⸻

Reviews MUST evaluate:

* correctness;

* maintainability;
* observability;
* scalability impact.

Reviews MUST reject:

* integration testing;

Testing MUST remain:

* deterministic;
* reproducible;

Critical systems SHOULD have:

* preserve invariants;

* preserve auditability;

* deployment behavior;
* rollback behavior;
* observability impact;
* scaling impact;
* replay behavior;
* failure modes.

Operational sustainability is part of engineering quality.

* asynchronous execution.

Distributed assumptions MUST remain explicit.

Build vs Buy Philosophy

The platform SHOULD:

* prefer mature stable primitives;
* avoid unnecessary reinvention.

The platform MUST avoid:

* framework worship;
* dependency-driven architecture;
* novelty engineering.

Technology choices MUST remain:

* operationally justified;
* maintainable for years.

⸻

Long-Term Engineering Goal

GPForum software engineering culture MUST remain:

* disciplined;
* constitution-driven;
* maintainable;
* security-focused;
* operationally sustainable;
* architecturally coherent.

Engineering is not feature accumulation.

Engineering is controlled long-term system design.

All future development MUST comply with this constitution.
