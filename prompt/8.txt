GPForum — Worker, Queue & Asynchronous Processing Constitution

Prompt 51 alignment: projection and outbox workers MUST remain idempotent,
retry-tolerant, restart-safe, replay-tolerant, duplicate-delivery-tolerant,
observable, and safe for projection lag reconciliation. Worker failure MUST NOT
corrupt canonical state or make derived state authoritative.

Prompt 45 alignment: workers MUST preserve idempotent, observable, replay-safe
contracts. Queue payloads MUST be versioned where long-lived, failures MUST be
classified, retries MUST be bounded, and asynchronous state MUST NOT become
authoritative.

This document defines the mandatory asynchronous processing architecture, worker orchestration philosophy, queue discipline, retry model, job lifecycle standards, distributed execution behavior, scheduling principles, and operational workload isolation model of GPForum.

This specification is foundational and mandatory.

⸻

Asynchronous Processing Philosophy

GPForum MUST operate as:

* asynchronous-first;
* event-driven;
* distributed;
* latency-aware.

The platform MUST avoid:

* blocking request workflows;
* synchronous heavy processing;
* request-bound orchestration;
* long-lived HTTP operations.

Asynchronous execution is foundational to:

* scalability;
* responsiveness;
* operational resilience;
* workload isolation.

⸻

Worker Philosophy

Workers are:

* distributed execution units;
* asynchronous orchestration processors;
* non-interactive execution systems.

Workers MUST remain:

* stateless;
* horizontally scalable;
* multi-process scalable;
* restart-safe;
* replay-tolerant.

Workers MUST tolerate:

* crashes;
* retries;
* duplicate delivery;
* delayed execution.

⸻

Mandatory Queue System

Preferred queue system:

* Minion.

Minion is the canonical asynchronous orchestration layer.

All slow or high-latency operations SHOULD execute through:

* queued jobs;
* asynchronous workflows;
* distributed workers;
* dynamically sized Perl worker pools.

⸻

Queue Ownership Philosophy

HTTP requests MUST:

* validate;
* persist authoritative state;
* emit events;
* enqueue asynchronous work.

HTTP requests MUST NOT:

* block on slow workflows;
* execute heavy orchestration;
* wait for distributed side effects.

Job Design Philosophy

Jobs MUST remain:

* deterministic;
* bounded;
* idempotent;
* observable;
* replay-safe.

Jobs SHOULD:

* perform one responsibility;
* remain composable;
* remain retry-safe.

⸻

Idempotency

All distributed jobs MUST support:

* idempotent execution.

Repeated execution MUST NOT:

* corrupt state;
* duplicate authoritative records;
* generate duplicate side effects;
* bypass authorization.

Idempotency is mandatory.

⸻

Retry Philosophy

Jobs MUST support:

* retry;
* bounded retry policies;
* exponential backoff;
* dead-letter handling.

Retries MUST remain:

* observable;
* auditable;
* failure-aware.

The system MUST tolerate transient failure.

⸻

Failure Isolation

Worker failure MUST NOT:

* crash application nodes;
* block HTTP traffic;
* corrupt persistence;
* halt unrelated workloads.

Worker queues SHOULD remain:

* isolated by responsibility;
* operationally separable.

Job Payload Philosophy

Job payloads SHOULD contain:

* identifiers;
* timestamps;

Jobs SHOULD avoid:

* giant embedded payloads;
* mutable embedded state;
* hidden authority assumptions.

Workers SHOULD retrieve authoritative state from PostgreSQL when required.
